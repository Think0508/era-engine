# 运行时修正 设计（属性临时修正 + 状态层数三层模型）

> 2026-09-22 定稿（用户逐问确认，多轮纠正后收敛）。目标：给属性有效值层补上**运行时来源** ——
> 临时改属性能"挂上去、到点自己消失"，**且基础值永生不被污染**；同时把**状态层数**（破绽/中毒层数）的
> 加减规则定清楚。
> 上游依据：`2026-09-22-attribute-effective-value-design.md`（有效值层总纲 D1–D7）与计划二（声明式来源，已合入 main）。
> 作者侧契约：`docs/attributes-system.md`。

## 1. 背景与缺口

| 步 | 内容 | 状态 |
|---|---|---|
| 计划一 | core 读取管线（闸门 + `compute` 派生 + 修正栈 + 叠加代数 + 缓存失效） | 已合入 |
| 计划二 | **声明式来源**（装备/被动技能/天赋，读时现算，不缓存、无需通知） | 已合入 |
| **本设计** | **运行时来源**（带到期时刻）+ 状态层数三层模型 | 待实施 |

缺口：修正栈只有代码 API（`registerModifier`），**没有数据驱动入口** —— 状态效果的 `modify_attribute` 直接写基础值（§2），
战斗效果没有"属性"这种落点，脚本/API 直挂没有时长概念，跨天状态无处存，状态层数只能整体加减（无法"护体 −1 层破绽"）。

## 2. 现状查证

### 2.1 状态效果的状态机已经存在，但 `modify_attribute` 写基础值（活雷）

`status-system` 已有：状态实例 `char.status_effects[] = { id, remaining_duration, stack, last_tick_game_time }`
（`src/plugins/status-system/index.ts:101-106`）、重复施加规则（`:92-98`）、时长倒计时 + 到期移除 + 按层数缩放的 tick（`:133-168`）、
条件别名（`:38-41`）。状态定义 schema 已有 `duration` / `tick_interval` / `stackable` / `max_stack` /
`on_apply_effects` / `on_remove_effects`（`mods/test-mod/definitions/status-effects.toml`）。

**雷**：

```toml
[status-effects."攻击增益"]
on_apply_effects  = [{ type = "modify_attribute", params = { attr = "attack", value = 10 } }]
on_remove_effects = [{ type = "modify_attribute", params = { attr = "attack", value = -10 } }]
```

`modify_attribute` 当前按"改基础值"实现 → 施加时 `attack = base + 10`，结束时 `−10` 减回去。
这不是"生效期间 +10"，而是**永久改了基础值再想办法减回去**：中间只要发生成长/其他改动/读档，减回去的数值就对不上，
**临时加成沉淀成永久属性**。本设计的第一验收点就是消灭它（§10 集成 2）。

### 2.2 时长追踪用「每小时硬扣 60 分钟」

`status.remaining_duration -= 60`（`:147`）假定每次 `game:hour_changed` 恰好过了 60 分钟；睡觉跨天/时间跳跃/非整点行动都会错。
改为**存到期时刻**（D3）。

### 2.3 状态层数只能整体加减

现有 `stack` 只能被"再次施加"递增（`:96-98`），**没有任何"别的效果改这条状态层数"的通道** ——
所以「护体：身上破绽恒 −1 层」今天无法表达（D11）。

## 3. 已定决策（用户确认）

| # | 决策 | 结论 |
|---|---|---|
| D1 | 三种"变化"分界 | **永久成长写基础值**（并在演出文本播报「xx+30 yy+60」）｜**临时修正进修正清单**｜派生由 `compute` 读时算。第一类绝不走修正，第二类绝不写基础值 |
| D2 | 属性临时修正存哪 | 实体上的 `char.attr_mods` 清单（纯数据字段 → 随存档往返零改动）；读属性时与声明式来源一起现算 |
| D3 | 到期怎么算 | 每条修正带**到期时刻**（绝对游戏分钟），`now >= expiresAt` 即失效。不用"剩余时长逐次扣减" |
| D4 | **不发明"差额"表示** | 「打到破绽3」写**定值**、「破绽+3」写**加法**、毒 −20% 写**倍率** —— 各写各的，**不互相换算**。效果到期撤销修正，**不需要记录"生效前是几"** |
| D5 | 顶替语义（同 (id, attr) 再次施加） | **两种运算，都必须明确**。①**「打到几」类（顶替）**：目标 `<=` 现有 → 无操作（**不降级、不刷新时长**）——这是用户明确要的：已有破绽3 时打「打到破绽3」或「打到破绽2」都不改变层数**也不刷新周期**；`>` → 顶上并**重置为新的完整时长**。②**一般重复施加（刷新类）**：强度**相等** → 顶上并刷新为新的完整时长（毒再中一次 = 刷新时间，数量不变）。运行时清单层按强度比较（`strength = set ?? flat ?? percent ?? 0`，老档条目缺省 = -Infinity）：`<` 现有 → 不生效且不刷新；`>=` → 顶上 + 刷新（与计划 Global Constraints 的 `strength` 比较一致）。**加法类（+N）不受顶替判定约束**（§5.1） |
| D6 | 时长单位 | **分钟**（沿用现有语义）：`4320` = 3 天。现有 中毒360/醉意120/攻击增益180 数据不动 |
| D7 | 状态效果并入 | `status-system` 新增 `attribute_mods`（属性临时修正）+ 到期改用 `expiresAt`；**移除 `on_apply_effects` 里"改 base"的 `modify_attribute` 用法** |
| D8 | 战斗效果落点 | `combat-base` 新增 `modify_attribute` 战斗动作；在既有 `recalcStats` 全量重算里按增量比对同步 push/remove；战斗结束清本场修正 |
| D9 | 封顶 | 本轮**不做**叠加封顶（YAGNI） |
| D10 | 收尾项 | 条件手册标注受修正字段、UI 基础/有效值差异呈现（`120 (+15)`）**不在本轮主刀** |
| D11 | **层数三层模型** | 状态的"有效层数" = **基础层数**（状态自带，招式改） + **层数修正**（其他状态给的 ±N，可撤销） − **时间衰减**。见 §5 |
| D12 | 层数修正的开放度 | **通用**：一个状态可以给自己身上的**任意**状态加减层数（护体减破绽、将来的"降低敌人破绽"招式同路） |
| D13 | 跨实体 | 本轮的修正一律作用于**目标自身**；"我的状态影响别人的属性"（跨实体）不在本轮（§12） |

## 4. 属性临时修正（运行时来源）

### 4.1 实体上的修正清单

```ts
// char.attr_mods: RuntimeAttrMod[]（缺省 = 空清单；旧存档天然如此）
interface RuntimeAttrMod {
  id: string              // 来源标识：状态用 `status:<状态ID>`，战斗用 `combat:<效果实例ID>`
  attr: string            // 属性名（mod 自定义字符串，core 不认识）
  flat?: number
  percent?: number
  set?: number
  expiresAt?: number      // 绝对游戏分钟；缺省 = 不自动到期（由来源显式移除）
  source?: string         // 可读来源说明（调试/UI）
}
```

- **它是「声明式来源」的第三个来源**，与装备/被动技能/天赋并列：读属性时现算，过期条目按 D3 跳过。
- 因此**不需要变更通知、不需要注销路径、不需要为"到期"发事件** —— 与计划二同一套推导式思想。
- 存实体字段而非独立命名空间：`save-system.ts:181` 对角色整体 `JSON.parse(JSON.stringify(c))`，
  **新增字段零改动随存档往返**；`restoreFromSave` 已有"缺字段按默认补 + warning"模式，**旧存档不需要迁移步骤**。

### 4.2 时间源注入

`attribute-eval.ts` 是叶子模块（只依赖 `error-reporter`），**不能 import `game-context`**。
到点判定需要"当前游戏分钟"，故由 `mod-loader` 在既有的 `configureAttributeEval(...)` 调用处**注入时钟**：

```ts
configureAttributeEval({ definitions, scriptResolver, defs, nowMinutes: () => gameTimeToTotalMinutes(ctx.time) })
```

未注入时（单测直接调本模块）按"无到期概念"处理：所有条目都算有效 —— 与其静默当作全部过期（会得到偏小的错误值），
不如当作不过期。

### 4.3 写法（各写各的，不换算）

| 作者写法 | 落到清单 | 语义 |
|---|---|---|
| `set = 3`（打到破绽3） | 定值 | 压过其它修正，破绽就是 3 |
| `flat = 3`（破绽+3） | 加法 | 与其它修正相加 |
| `percent = -0.2`（毒 −20%） | 倍率 | 与其它 percent 相加后只乘一次 |

**不加"差额"换算**（D4）：作者写什么就是什么，叠加代数照旧 `((set ?? 值) + Σflat) × (1 + Σpercent)`。
在有 `+20%` 的属性上写「+20」就得到 `(base+20)×1.2` —— 这是正确的，百分比本就该作用于它。

## 5. 状态层数三层模型（D11/D12）

```
状态有效层数 = 基础层数（base_stack）
             + Σ 层数修正（stack_mods：其他/自己的状态给的 ±N）
             − 时间衰减（decay）
             （下限 0；为 0 时状态可结束）
```

### 5.1 基础层数（状态自带）

**招式的表达方式**：`apply_status` 效果扩展一个可选参数 `stack`，招式/战斗效果库条目按需给定：

```toml
# 招式：打到破绽3（定层）
effects = [{ type = "apply_status", params = { status = "破绽", stack = 3 } }]
# 招式：破绽+3（加层）
effects = [{ type = "apply_status", params = { status = "破绽", stack_add = 3 } }]
# 不带这两个参数 = 按状态定义默认（现有行为）
effects = [{ type = "apply_status", params = { status = "中毒" } }]
```

- 「打到破绽N」→ 对**目标**的那条状态：`base_stack = max(base_stack, N)`；`N <= 现有` → **无操作**（D5 ①「打到几」类：不降级、不刷新时长；至于"一般重复施加、强度相等 → 刷新时长"是 D5 ②，那是清单层的规则，不适用于本行的定层运算）
- 「破绽+N」→ `base_stack += N`（加法，不受 D5 顶替判定约束，见下方注）
- 顶替成功时**重置状态到期时刻**为新的完整时长（D5）
- 基础层数**随状态实例存亡**：状态到期 → 整条消失（不需要"还原成打之前几层"）
- 时间衰减：定义里声明（如 `stack_decay = { every = 60, amount = 1 }`），每 `every` 分钟 −`amount` 层，到 0 层状态结束

> **加法类（`stack_add`）与顶替类（`stack`）是两种运算**（用户确认的两个例子）：
> 「破绽+3」是"在当前基础上加"，「打到破绽3」是"打到某一层"。
>
> | 当前 | 打上来 | 结果 |
> |---|---|---|
> | 破绽1 | 破绽+3 | 破绽4 |
> | 破绽0 | 破绽+5 | 破绽5 |
> | 破绽5 | 打到破绽3 | **无操作**（3 顶不掉 5），但该次攻击照样享受破绽5 的减益 |
>
> 即：**加法恒生效地加**；"打到几"只在超过当前时才顶替（D5 只约束这一种）。

### 5.2 层数修正（D12 的新能力）

状态定义里声明"给某个状态的层数 ±N"：

```toml
[status-effects."护体"]
name = "护体"
duration = 4320
stack_mods = [ { status = "破绽", value = -1 } ]   # 身上破绽恒 −1 层（最小 0，0 层默认不显示）
```

- 修正挂在**目标状态**上，记 `{ from: "护体", value: -1, expiresAt }`：明确"谁给的"，便于撤销与排查
- **到期或来源状态被移除 → 撤销修正，基础层数分毫不动** —— 这就是"不需要记录生效前是几"的实现方式
- 修正自身可有独立到期时刻；缺省跟随**来源状态**的生灭（"恒 −1"即此意）
- 下限 0；有效层数为 0 时该状态**默认不显示**（显示层由 UI 决定）

### 5.3 与属性层的关系

层数模型**属于状态系统**（用户裁定：破绽是状态层数，不是角色属性）。
若某条状态同时声明了 `attribute_mods`，那是"这条状态生效期间给角色属性的修正"，与它的层数是两件事：
层数决定"这条状态多强"（影响 tick 缩放等），`attribute_mods` 决定"它给角色加了什么属性"。

## 6. 到期与结算

- **属性修正**：`now >= expiresAt` 即不参与聚合。两处保证正确：
  1. **读属性时**跳过过期条目并顺手剪除 —— 兜底，任何读取都正确
  2. **`game:hour_changed`**（沿用 status-system 既有结算时机）—— 负责"到期副作用"（执行 `on_remove_effects` 的非属性效果、撤销层数修正、播报）
- **状态到期**：整条状态移除（层数与它的层数修正一起消失）
- **时间跳跃天然正确**：存绝对时刻，睡 8 小时直接越过 `expiresAt`，不会少扣或多扣
- **时停守卫照旧**：`status-system` 已有的 `h-time-stop` 早退（`index.ts:66-71`）保留

## 7. 消费方

### 7.1 status-system

- 状态定义新增 `attribute_mods`（属性临时修正）与 `stack_mods`（层数修正）
- 施加：按 §4.3/§5.1 写基础层数 + push 带到期时刻的属性修正
- 重复施加按 D5：清单层 `<` 现有强度 → 无操作（不降级、不刷新时长）；`>=`（含**同强度**）→ 顶上并刷新为新的完整时长（毒再中一次 = 刷新时间，数量不变）；层数侧按 §5.1 的「打到几」/「+N」两类各走各的
- 到期/移除：撤销属性修正与层数修正（**不碰基础值、不碰基础层数**）
- **`on_apply_effects` / `on_remove_effects` 定位收窄**：仅用于"一次性、非属性/非层数"的效果。
  **禁止用它们做临时属性加成**（那正是 §2.1 的雷）。永久属性成长也不走状态效果 —— 按 D1 直接写基础值并由发起方播报

### 7.2 combat-base

- 新增战斗动作 `modify_attribute`：`action = "modify_attribute"` + `attr` + `value = { flat?/percent?/set? }`
- **同步时机复用 `recalcStats`**：该函数本就每次结算把效果区**全量重算**（`combat-base/index.ts:1028-1041`），
  是天然的幂等挂载点 —— 不新增钩子，不做"挂载注册/卸下注销"的配对逻辑
- **增量比对**：本场所需修正的签名（实例 id + 属性 + 数值）与上一轮比对，**只在签名变化时**才写实体清单，
  避免每次重算都 bump 缓存版本
- 战斗结束清掉本场修正（`id` 前缀 `combat:` 便于整批移除）
- 招式对目标层数的作用（打到破绽N / 破绽+N）走 §5.1，与属性修正分开

## 8. 加载期校验

沿用计划二 `validateAttributeMods` 的位置与姿态（`mod-validate.ts`，report-only、`severity: 'error'`、不抛错）：

- 状态定义 / 战斗效果库条目的属性修正：属性必须已定义、`flat/percent/set` 至少一项
- **`per_level` 只允许用在"被动技能 / 天赋"两类**（计划二已定）。状态定义与战斗效果**都无等级概念** →
  写了 `per_level` = 加载期 error（不静默当 1 级）。运行时来源的数值一律按"施加那一刻算好"的定值写入
- `action = "modify_attribute"` 必须带 `attr` 且该属性已定义（否则效果静默无效 —— 这正是校验存在的意义）
- `stack_mods`：`status` 必须指向已定义的状态、`value` 必须是非零整数；`stack_decay` 的 `every > 0`、`amount > 0`
- `apply_status` 的 `stack` / `stack_add`：必须是非负整数，且**不得同时给**（一个"打到几"、一个"加几"，同给无语义）
- 状态 `duration` 必须是有限数字（或 `-1` = 永久）

## 9. 连带影响

| 影响面 | 说明 |
|---|---|
| **存档** | `char.attr_mods` 与状态实例的 `expiresAt`/`base_stack`/层数修正随角色整体序列化，零改动；旧存档缺字段 → 默认值，**无需迁移步骤** |
| **读-改-写** | 不变量照旧：要写回哪个值就从哪个值出发读（`applyAttrDelta` / `readRawAttr` / `getRaw`）。临时修正**永不写回基础值** |
| **条件表达式** | 走同一读取入口 → 自动看到有效值（中毒降灵敏后条件按降低值判）；层数条件看**有效层数**（含护体 −1） |
| **缓存** | 运行时修正与声明式修正同路：实体只要有修正，该实体读取不进缓存（计划二的 `cacheable` 策略原样适用） |
| **现有数据** | `攻击增益` 必须从"改 base"迁移为 `attribute_mods`；`中毒`/`醉意` 的 `duration` 语义不变（分钟） |

## 10. 验证要点

**单元**
- 属性修正到期：`now < expiresAt` 生效 / `now >= expiresAt` 失效；过期条目被剪除；时间跳跃后直接失效
- **不污染基础值**（核心不变量）：挂修正期间反复读取、并经正常写入路径（`setEntityAttr` / `applyAttrDelta`）改基础值多次，
  `readRawAttr` 始终不含临时修正；修正到期后有效值 == 基础值 + 其余修正
- 顶替（D5）两层规则都要覆盖：**「打到几」类** 目标 `<=` 现有 → 无操作且**时长也不刷新**（破绽3 时打「打到破绽3」/「打到破绽2」都不变层数、不刷新周期）、`>` → 顶上 + 时长重置为新的完整时长；**一般重复施加** 强度相等 → 顶上并刷新为新的完整时长（毒再中一次 = 刷新时间）。清单层按 `strength` 比较：`<` 不生效且不刷新 / `>=` 顶上 + 刷新
- 层数三层：基础层数 + 层数修正（护体 −1）+ 衰减；下限 0；**来源状态移除 → 层数修正撤销、基础层数不变**
- 三源共存：装备（声明式）+ 状态（运行时）+ 战斗修正叠加走同一份代数（percent 相加只乘一次）

**集成**
1. 中毒（`attribute_mods` 降灵敏）→ 属性与条件判断跟着变 → 到期 → **自动回落（无还原代码）**
2. **攻击增益**：施加时 `attack` 有效值 +10，而 `readRawAttr` 仍是原值；到期后回到原值
   （对照 §2.1 的雷 —— 本设计第一验收点）
3. 战斗效果 `modify_attribute`：战斗中属性变化 → 战斗结束 → 回落
4. 护体 −1 层破绽：护体在 → 破绽显示减 1；护体到期 → 破绽恢复，**基础层数不变**
5. 存档往返：带未到期状态存档 → 读档 → 剩余时长、基础层数、层数修正均正确恢复；已过期条目不生效
6. 时间跳跃：睡 8 小时越过 `expiresAt` → 状态到期，不出现"少扣/多扣"

## 11. 不做（YAGNI）

- 叠加层数封顶（D9）
- 跨实体属性修正（别人的状态改我的属性）—— 独立议题（§12）
- 内功装配（`equipped_mods`）：属秘籍/内功系统（装配槽、装配指令、排他规则、UI）
- 条件手册标注受修正字段、UI 基础/有效值差异呈现（D10）
- 状态时长结构化 `{ days = 3 }`（D6：保持分钟）
- 秘籍/技能系统本身

## 12. 范围之外（后续独立议题）

- **跨实体修正**："甲的状态影响乙的属性"需要"来源实体 → 目标实体"的方向与优先级。本轮的层数修正与属性修正
  一律作用于**目标自身**（招式打别人时，"目标"就是被打的人）。
- **秘籍系统与内功装配**：装配期间生效的 `equipped_mods` 只是"多一个来源"，但装配槽/排他规则/装配指令属玩法机制。
- **技能威力公式**：威力不是属性，属技能 schema。
- **破绽的战术意义**（破绽高了会怎样）：属战斗玩法设计，引擎只提供层数与读取。
