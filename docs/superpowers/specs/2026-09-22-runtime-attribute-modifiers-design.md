# 运行时属性修正 设计（带到期时刻的修正 + 状态/战斗两个消费方）

> 2026-09-22 定稿（用户逐问确认）。目标：给属性有效值层补上**运行时（push）来源** —— 临时改属性要能"挂上去、到点自己消失"，**且基础值永生不被污染**。
> 上游依据：`2026-09-22-attribute-effective-value-design.md`（有效值层总纲，D1–D7）与计划二（声明式来源，已合入 main）。
> 作者侧契约：`docs/attributes-system.md`。

## 1. 背景：现状与缺口

属性有效值层已分两步落地：

| 步 | 内容 | 状态 |
|---|---|---|
| 计划一 | core 读取管线（闸门 + `compute` 派生 + 修正栈 + 叠加代数 + 缓存失效） | 已合入 |
| 计划二 | **声明式来源**（装备/被动技能/天赋，读时现算，不缓存、无需通知） | 已合入 |

**缺口：运行时来源一条都没有。** 修正栈只有代码 API（`registerModifier`），**没有数据驱动入口**：

- 状态效果的 `modify_attribute` **直接写基础值**（见 §2 的雷）
- 战斗效果的 `action` 只有 `modify_stat`（战斗统计键）与 `modify_channel`（公式通道），**属性是第三种落点，目前不存在**
- 脚本/API 直挂没有时长概念，跨天状态无处存

## 2. 现状查证：状态效果已经在做这件事（做错了一半）

`status-system` 已有一套完整的运行时状态机，**施加语义与本设计所需的规则几乎一致**：

| 事实 | 证据 |
|---|---|
| 状态实例存 `char.status_effects[] = { id, remaining_duration, stack, last_tick_game_time }` | `src/plugins/status-system/index.ts:101-106` |
| 重复施加的叠加规则已实现：不叠则只刷新时长；可叠则 +1 层封顶 `max_stack` | `:92-98` |
| 时长倒计时 + 到期移除 + 结算 tick（按层数缩放） | `:133-168` |
| 状态定义 schema 已有 `duration` / `tick_interval` / `stackable` / `max_stack` / `on_apply_effects` / `on_remove_effects` | `mods/test-mod/definitions/status-effects.toml` |
| 条件别名已接（`status.*` / `remaining`） | `:38-41` |

### 2.1 雷：`modify_attribute` 写基础值，临时 buff 被永久烘进 base

```toml
[status-effects."攻击增益"]
on_apply_effects  = [{ type = "modify_attribute", params = { attr = "attack", value = 10 } }]
on_remove_effects = [{ type = "modify_attribute", params = { attr = "attack", value = -10 } }]
```

`modify_attribute` 当前按"改基础值"实现。于是：施加时 `attack = base + 10`，结束时再 `−10` 回来。
后果与 spec §10 验证要点 4 完全同类：**这不是"生效期间 +10"，而是"永久改了基础值再想办法减回去"** ——
中间只要发生一次成长/其他改动/存档读档，减回去的数值就对不上，临时加成会**沉淀成永久属性**。

### 2.2 时长追踪用「每小时硬扣 60 分钟」

`status.remaining_duration -= 60`（`:147`）假定"每次 `game:hour_changed` 恰好过了 60 分钟"。
睡觉跨天、时间跳跃、行动耗时不是整点时，扣减与实际经过时间不一致。用户已裁定改为**存到期时刻**（D3）。

## 3. 已定决策（用户确认）

| # | 决策 | 结论 |
|---|---|---|
| D1 | 三种"属性变化"分界 | **永久成长写基础值**（并在演出文本里播报「xx+30 yy+60」）｜**临时修正进修正清单**｜派生由 `compute` 读时算。**第一类绝不走修正，第二类绝不写基础值** |
| D2 | 临时修正存哪 | 实体上的 `char.attr_mods` 清单（纯数据字段 → 随存档往返零改动）；读属性时与声明式来源一起现算 |
| D3 | 到期怎么算 | 每条修正带**到期时刻**（绝对游戏分钟），判定 `now >= expiresAt` 即失效。不用"剩余时长逐次扣减" |
| D4 | 施加语义 | **运算只对"当前结果"做一次，结果写回基础层数**；效果本身带到期时刻，只负责临时修正的生灭。**不需要记录"生效前是几"这种历史** |
| D5 | 强弱判定 | 新施加的**结果层数**若 `<=` 现有层数 → **什么都不发生**（不降级、不刷新时长）；若 `>` → 顶上并**重置为新的完整时长** |
| D6 | 时长单位 | **分钟**（沿用现有语义）：`4320` = 3 天。现有 中毒360/醉意120/攻击增益180 数据不动 |
| D7 | 状态效果并入 | `status-system` 的 `attribute_mods` + 到期改用 `expiresAt`；**移除 `on_apply_effects` 里"改 base"的 `modify_attribute` 用法** |
| D8 | 战斗效果落点 | `combat-base` 新增 `modify_attribute` 战斗动作；在既有 `recalcStats` 全量重算里按增量比对同步 push/remove；战斗结束清本场修正 |
| D9 | 封顶 | 本轮**不做**叠加封顶（YAGNI）；需要时下轮补 |
| D10 | 收尾项 | 条件手册标注受修正字段、UI 基础/有效值差异呈现（`120 (+15)`）**不在本轮主刀** |

## 4. 数据模型

### 4.1 实体上的运行时修正清单

```ts
// char.attr_mods: RuntimeModEntry[]（缺省 = 空清单；旧存档天然如此）
interface RuntimeModEntry {
  id: string              // 来源标识：状态用 `status:<状态ID>`，战斗用 `combat:<参战者>:<效果实例ID>`
  attr: string            // 属性名（mod 自定义字符串，core 不认识）
  flat?: number
  percent?: number
  set?: number
  expiresAt?: number      // 绝对游戏分钟；缺省 = 不自动到期（由来源显式移除）
  source?: string         // 可读来源说明（调试/UI）
}
```

- **它就是「声明式来源」的第三个来源**，与装备/被动技能/天赋并列：读属性时现算，过期条目按 D3 跳过。
- 因此**不需要变更通知、不需要注销路径、不需要为"到期"发事件** —— 与计划二同一套推导式思想。
- 存放位置选实体字段而非独立命名空间：`save-system.ts:181` 对角色整体 `JSON.parse(JSON.stringify(c))`，
  **新增字段零改动随存档往返**；`restoreFromSave` 已有"缺字段按默认补 + warning"模式，**旧存档不需要迁移步骤**。

### 4.2 时间源注入

`attribute-eval.ts` 是叶子模块（只依赖 `error-reporter`），**不能 import `game-context`**。
到点判定需要"当前游戏分钟"，故由 `mod-loader` 在既有的 `configureAttributeEval(...)` 调用处**注入时钟**：

```ts
configureAttributeEval({ definitions, scriptResolver, defs, nowMinutes: () => gameTimeToTotalMinutes(ctx.time) })
```

未注入时（单测直接调本模块）按"无到期概念"处理：所有条目都算有效 —— 与其静默当作全部过期（会得到错误的偏小值），不如当作不过期。

## 5. 运算与施加语义（D4 / D5）

### 5.1 运算只对"当前结果"做一次

属性读出来的**有效值**就是"当前结果"（基础值 + 声明式修正 + 运行时修正，经同一份叠加代数）。
新效果到来时，用当前结果算出新结果，然后把**差额**写成一条带到期时刻的临时修正：

```
当前有效值 v = readEffective(char, attr, raw)
新结果       v' = 按效果定义运算(v)        // 运算见 §5.2
差额         d  = v' - v                  // §5.2 的三条运算保证 d >= 0
临时修正     push { id: "status:中毒", attr, flat: d, expiresAt }
```

> ⚠️ **基础值不参与这个差额**：差额写的是"相对当前有效值"的临时修正，基础值原样不动。
> 到期时撤销该条修正，属性自动回落到"基础值 + 其余修正"，**无需还原代码**（D4）。

**差额只加不减**：§5.2 的三条运算都保证结果 `>=` 当前值，所以 `d >= 0`，不存在"临时扣属性"的路径。
这条限制是有意的 —— 它让"新施加是否顶替"永远退化成一次简单的大小比较（D5）。

**差额落在哪个域（精度问题）**：临时修正写 `flat: d`。由于叠加代数里 `flat` 在 `percent` **之前**相加
（`((set ?? v) + Σflat) × (1 + Σpercent)`），若该属性上同时挂着百分比修正，写 `flat: d` 会让差额也被百分比放大
（例如基础 100 挂 +20%、效果要加到 120：`d = 20`，写 flat 后算得 `(100+20)×1.2 = 144 ≠ 120`）。
因此：**属性上存在 `percent` 类修正时，差额改写为 `set: v'`**（定值语义天然精确，不受 percent 影响）；
无 `percent` 修正时才用 `flat: d`（更易读、且与声明式来源的数值可比）。判定时机 = 施加那一刻，写死在条目里。

### 5.2 「打到 N」与「+N」两类运算

用户明确两类都要做，且**都只输出一个结果层数**：

| 效果写法 | 运算 | 例（当前破绽1） |
|---|---|---|
| 打到 N（目标层数） | `v' = max(v, N)` | 打到破绽3 → 3 |
| 加 N | `v' = v + N` | 破绽+3 → 4 |
| 减 N | `v' = max(0, v - N)` | 破绽−3 → 0（下限 0） |

**判定统一按结果层数比大小**（D5）：结果 `<=` 当前 → 无操作；结果 `>` 当前 → 顶上 + 重置时长。
不再引入"类型优先级"之类的额外规矩（用户已否决：比数字即可）。

## 6. 到期与结算

- **到期判定**：`now >= expiresAt` 即该条修正不参与聚合。挂在两个位置：
  1. **读属性时**（聚合时跳过过期条目，并顺手把过期条目从清单里剪掉）—— 兜底，保证任何读取都正确
  2. **`game:hour_changed`**（沿用 status-system 既有的结算时机）—— 负责触发 `on_remove_effects` 的
     "到期副作用"（如状态结束时要执行的非属性效果）
- **时间跳跃天然正确**：存的是绝对时刻，睡觉跨天直接越过 `expiresAt` 即失效，不会少扣或多扣。
- **时停守卫照旧**：`status-system` 已有的 `h-time-stop` 早退（`index.ts:66-71`）保留 —— 时停中状态不结算。

## 7. 两个消费方

### 7.1 status-system（状态效果）

- 状态定义新增 `attribute_mods = [{ attr, flat?, percent?, set? }]`（形状与计划二一致；状态无等级概念，
  故 **`per_level` 在状态定义上 = 加载期 error**，与装备同理）
- 施加时：按 §5 算差额 → push 一条 `id = "status:<状态ID>"` 的带到期修正
- 重复施加按 D5（结果 `>` 才顶替并重置时长；否则无操作）
- 到期/移除时：删掉该条修正（**不碰基础值**）→ 属性自动回落
- **`on_apply_effects` / `on_remove_effects` 的定位收窄**：仅用于"一次性、非属性"的效果。
  **禁止用它们做临时属性加成**（那正是 §2.1 的雷）。永久属性成长也不走状态效果 ——
  按 D1 直接写基础值，并由发起方播报演出文本。

### 7.2 combat-base（战斗效果）

- 新增战斗动作 `modify_attribute`：`action = "modify_attribute"` + `attr` 字段 + `value = { flat?/percent?/set? }`
- **同步时机复用 `recalcStats`**：该函数本来就每次战斗结算把效果区**全量重算**（`combat-base/index.ts:1028-1041`），
  是天然的幂等挂载点 —— 不新增钩子、不做"挂载时注册、卸下时注销"的配对逻辑
- **增量比对**：把本场需要的修正签名（实例 id + 属性 + 数值）与上一轮比对，**只在签名变化时**才写实体清单，
  避免每次重算都 bump 缓存版本
- 战斗结束清掉本场修正（`id` 前缀 `combat:` 便于整批移除）

> 「护体：身上破绽恒 −1」这类**跨实体**的效果（甲的状态影响乙的属性）本轮**不做**：
> 它需要"来源实体 → 目标实体"的修正方向，属独立议题（§12）。

## 8. 加载期校验

沿用计划二 `validateAttributeMods` 的位置与姿态（`mod-validate.ts`，report-only、`severity: 'error'`、不抛错），新增：

- 状态定义 / 战斗效果库条目的 `attribute_mods` / `value` 走同一套校验：属性必须已定义、`flat/percent/set` 至少一项
- **`per_level` 的适用范围收紧为"被动技能 / 天赋"两类**（计划二已定）。状态定义与战斗效果**都无等级概念**，
  写了 `per_level` → **加载期 error**（不静默当 1 级）。这同时意味着 `scaleByLevel` 只服务声明式来源，
  运行时来源的数值一律按"施加那一刻算好"的定值写入条目
- `action = "modify_attribute"` 必须带 `attr` 且该属性已定义（**否则效果静默无效** —— 这正是校验存在的意义）
- 状态的 `duration` 必须是有限数字（或 `-1` 表示永久）

## 9. 连带影响

| 影响面 | 说明 |
|---|---|
| **存档** | `char.attr_mods` 随角色整体序列化，零改动；旧存档缺字段 → 空清单，**无需迁移步骤** |
| **读-改-写** | 不变量照旧：要写回哪个值就从哪个值出发读（`applyAttrDelta` / `readRawAttr` / `getRaw`）。临时修正**永不被写回基础值** |
| **条件表达式** | 走同一读取入口 → 自动看到有效值（中毒降灵敏后条件按降低值判），这是 D1「全局」的应有之义 |
| **缓存** | 运行时修正与声明式修正同路：实体只要有修正，该实体读取不进缓存（计划二的 `cacheable` 策略原样适用） |
| **状态效果与属性修正的一致性** | 状态的显示层数 = 基础层数 + 临时修正（如护体 4−1 显示 3），与 D4「身上永远只是当前结果」一致 |

## 10. 验证要点

**单元**
- 到期：`now < expiresAt` 生效 / `now >= expiresAt` 失效；过期条目被剪除；时间跳跃后直接失效
- 施加（D5）：结果 `<=` 当前 → 无操作且**时长也不刷新**；结果 `>` → 顶上 + 时长重置为新的完整时长
- 运算（§5.2）：打到 N = `max(v,N)`；+N；−N 且有 0 下限
- **不污染基础值**（核心不变量）：挂修正期间反复读取、并**经正常写入路径修改基础值**（`setEntityAttr` /
  `applyAttrDelta`）多次，`readRawAttr` 读到的始终不含临时修正；修正到期后有效值 == 基础值 + 其余修正
- 与声明式来源共存：装备 + 状态 + 战斗修正三者叠加走同一份代数（percent 相加只乘一次）

**集成**
1. 中毒（含 `attribute_mods`，如灵敏 −20%）→ 属性与条件判断跟着变 → 到期 → **自动回落（无还原代码）**
2. 攻击增益：施加时 `attack` 显示 +10，**`readRawAttr` 仍是原值**；到期后回到原值（对照 §2.1 的雷，此为本设计的第一验收点）
3. 战斗效果 `modify_attribute`：战斗中属性变化 → 战斗结束 → 回落
4. 存档往返：带未到期状态存档 → 读档 → 剩余时长与修正均正确恢复；已过期条目读档后不生效
5. 时间跳跃：睡 8 小时越过 `expiresAt` → 状态到期，不出现"少扣/多扣"

## 11. 不做（YAGNI）

- 叠加层数封顶（D9）
- 跨实体修正（甲的护体减乙的破绽）—— 独立议题
- 内功装配（`equipped_mods`）：属秘籍/内功系统的玩法机制（装配槽、装配指令、排他规则、UI）
- 条件手册标注受修正字段、UI 基础/有效值差异呈现（D10）
- 状态时长单位改为结构化 `{ days = 3 }`（D6：保持分钟）
- 秘籍/技能系统本身

## 12. 范围之外（后续独立议题）

- **跨实体属性修正**：「护体：身上破绽恒 −1」这类"我的状态影响你的属性"，需要修正方向（来源实体 → 目标实体）与
  叠加优先级，属独立设计。本轮修正一律作用于**目标自身**。
- **秘籍系统与内功装配**：装配期间生效的 `equipped_mods` 只是"多一个来源"，但装配槽/排他规则/装配指令属玩法机制。
- **技能威力公式**：威力不是属性，属技能 schema。
- **状态层数的自然衰减**：破绽是否随时间自行减少、按什么速率，属具体玩法的状态定义规则（`tick_effects` 已能表达），
  引擎不预设。
